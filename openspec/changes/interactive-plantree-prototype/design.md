## Context

PlanTree 要验证“用户编辑任务树后，Agent 能重新取得一致计划”这一交互假设。当前没有实现代码，也没有可复现实验环境。首个交付不再是独立浏览器应用，而是可在 Codex 中安装的本地插件：MCP 服务保存计划状态和执行领域逻辑，MCP App 小窗作为会话内的交互入口。

该形态直接服务后续 Codex 集成。演示者可在持续对话的同时查看和编辑任务树；项目组成员可通过结构化 MCP 工具获取同样的状态；后续实验实现者可替换模拟规划器而不改变 UI 协议。真实 LLM、SWE-bench 与三组对照实验仍属于后续变更。

## Goals / Non-Goals

**Goals:**

- 交付一个带 `.codex-plugin/plugin.json` 的本地 Codex 插件，并可通过本地 marketplace 安装和测试。
- 通过 MCP 服务提供创建/加载会话、编辑、重规划、验证、模拟执行、撤销、重置和渲染计划的工具。
- 通过 MCP App UI 将交互式任务树显示为 Codex 会话内的 Picture-in-Picture 小窗，而不是启动独立浏览器。
- 将任务树、编辑命令、规划器、验证器、执行模拟器与审计日志保持为纯领域模块。
- 使用确定性模拟规划器，使同一输入得到同一结果，并为未来真实 Codex/LLM 适配保留稳定边界。

**Non-Goals:**

- 不构建独立网页、独立桌面应用、原生 Win32 窗口或外部浏览器标签页。
- 不调用真实 LLM、网络服务、SWE-bench、GitHub、终端、容器或代码执行环境。
- 不测量模型成本、Token、端到端延迟或任务解决率。
- 不实现多用户协作、鉴权、云端持久化、跨会话撤销或通用工作流编排。

## Decisions

### 1. 以 Codex 插件承载能力边界

插件包包括 manifest、一个识别 PlanTree 工作流的技能、MCP 服务和 MCP App UI 资源。技能负责让 Codex 在用户需要检查、编辑或重规划任务树时调用工具；MCP 服务负责权威业务状态；UI 只负责显示与用户输入。

选择原因：官方插件形态可组合 skill、MCP server 与可选 UI，能直接安装在 Codex 中。替代方案是先做独立桌面程序再连接插件；它会增加两个独立生命周期、安装步骤和同步协议。

### 2. 用本地 stdio MCP 服务保存权威状态

MCP 服务在插件安装后由 Codex 本地启动，并在进程内保存单次会话的计划、版本、撤销栈和审计日志。所有界面操作都必须经由 MCP 工具调用，工具返回更新后的结构化计划快照与文本摘要。服务端模块不得依赖 UI 或 Codex 宿主 API。

选择原因：MCP 工具即使在 UI 不支持或未渲染的客户端仍可工作，且工具结果可直接进入对话上下文。替代方案是把状态放在小窗中；刷新、重渲染或无 UI 场景会丢失权威数据。

### 3. 使用 MCP App Picture-in-Picture 小窗

服务只把 UI 资源关联到 `render_plan_tree` 工具。该工具接受权威计划快照并返回 `structuredContent` 与 MCP App UI resource URI；小窗使用 MCP Apps bridge 调用编辑、执行、撤销和重置工具，再使用服务器返回的快照刷新。UI 自身仅保存选中节点、展开状态和未提交表单等临时展示状态。

选择原因：Picture-in-Picture 让任务树在对话过程中保持可见，又不打开独立浏览器。替代方案是对每个数据工具都附加 UI；这会频繁重建小窗并使模型工具链难以复用。

### 4. 保留纯函数的确定性领域层

任务树以一个根节点、节点字典、稳定 ID、父子关系、显式依赖和版本化元数据表达。编辑工具先生成快照，再顺序执行影响范围分析、局部重规划、依赖同步、有效性检查和审计追加。规划器不得读取时间、随机数、外部文件或网络。

选择原因：把交互语义与模型不确定性隔离，便于测试，也为真实规划器替换留下接口。替代方案是将规则混入 MCP tool handler；它会阻碍对领域逻辑的单独验证。

### 5. 采用数据工具与渲染工具分离模式

`create_or_load_demo`、`edit_node`、`simulate_execution`、`undo_last_edit` 与 `reset_demo` 是数据工具，不绑定 UI；`render_plan_tree` 是唯一返回小窗资源的渲染工具。每个数据工具均返回完整 `structuredContent`，从而使 Codex 能在无 UI 时描述或继续执行工作流。

选择原因：符合官方 MCP App 的数据处理与呈现分离建议，避免小窗在每次编辑时无意义重载。替代方案是将 UI 模板绑定到全部工具；其状态和性能更难控制。

## Architecture

```text
Codex 用户 / PlanTree skill
            |
            v
  本地 stdio MCP 服务
  |         |          |
  |         |          +--> render_plan_tree --> MCP App PiP 小窗
  |         |                                      |
  |         +<------ tools/call via MCP Apps bridge+
  |
  +--> 会话控制器
         -> 编辑命令
         -> 影响范围分析
         -> 确定性模拟规划器
         -> 依赖同步与验证
         -> 模拟执行与审计日志
```

MCP 服务是计划和日志的唯一权威来源。小窗收到工具结果后渲染；它不直接修改计划。小窗向 MCP 服务请求状态改变后，服务重新返回快照；小窗保留仍兼容的临时展示状态。

## Risks / Trade-offs

- [Codex 环境未呈现某种 UI 模式] -> 所有数据工具均返回完整结构化状态与文本摘要；PlanTree 不依赖小窗才能完成核心流程。
- [小窗 iframe 与原生桌面窗口混淆] -> 在演示文档中明确：它是 Codex 内嵌 PiP，不会启动外部浏览器，但不是 Win32 窗口。
- [stdio 服务状态在插件重启后丢失] -> 将单会话内存状态列为第一阶段边界，并提供确定性的演示重置；持久化后续单独设计。
- [UI 重渲染造成临时状态丢失] -> 让选中节点、展开状态与表单草稿保留在 UI，并以最近服务端快照作为业务数据源。
- [模拟规则无法代表真实 LLM 规划质量] -> 仅用其验证交互和一致性；真实规划器与基准实验留给后续变更。

## Migration Plan

本变更没有既有实现需要迁移。实施顺序为：先完成纯领域模块及测试，再以本地 stdio MCP server 暴露工具，之后将小窗资源与工具桥接，最后用本地 marketplace 安装并在 Codex 中走查。若要回滚，移除本地 marketplace 中的插件条目即可，不影响外部数据或服务。

## Open Questions

- 是否在第一版加入重规划前后差异视图；当前规格只要求审计可追溯与影响范围可见。
